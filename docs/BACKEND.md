# Backend setup

For current tool inputs and endpoints, use [the shared API reference](../agents/API.md). For connection setup and version-safe operations, use [the agent guide](../agents/README.md). This page covers the underlying database/bootstrap setup.

1. Apply all SQL files in `supabase/migrations/` in filename order using the Supabase SQL editor or migration tooling as the database administrator. The `pm_` tables and `pm-documents` bucket are independent of the walkthrough application's tables.
2. Provision the first administrator with `scripts/provision-admin.mjs`. Read its environment variable names, load secrets privately and do not commit them. It creates a confirmed Auth user if absent; an existing user's password stays unchanged unless `PM_RESET_PASSWORD=true` is explicitly set. There is no public signup or automatic workspace membership.
3. Configure only `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` for the app. Never configure a service role key in the application runtime. The admin provisioning script is the only consumer of an elevated key.
4. Deploy and sign in, then create the explicitly labeled demo using the New project wizard. Real projects are created without fictional data.

All API requests require `Authorization: Bearer <Supabase access token>`. Supabase `getUser` validates the token. The default workspace is the oldest membership; an optional `x-workspace-id` header selects another workspace only if the caller belongs to it. `reader` is read-only; `admin` and `manager` can operate the manual tool. Authenticated users have SELECT-only table grants and RLS. Writes use narrow RPC functions that check the JWT identity's workspace role, expected versions, links and workflow gates. New project plus template rows, imports and each edit/audit insertion are atomic database transactions. Audit before/after snapshots are retained; the Activity view returns the latest 250 event summaries.

Record and project edits send `version`. Stale writes return HTTP 409 and do not overwrite a newer version. Source references and required links are preserved. A customer-derived prerequisite can be recorded as not applicable with a reason; its source row is not deleted. Project IDs and record kinds cannot be changed in-place.

Files use private `pm-documents` Storage, a 20 MB bucket limit and allowed MIME types. The browser first calls `POST /api/files/prepare` with `{name,size,project_id,title,category,record_id?}`, uploads to Supabase with the returned `path`, `token` and `contentType`, then calls `POST /api/files/complete` with the same metadata and `path`. Finalization checks actual downloaded size and file signatures before storing a document record. This avoids the Vercel 4.5 MB function request limit. The legacy multipart `POST /api/files` is limited to 4 MB. `GET /api/files/:id` verifies membership and returns a 60-second attachment download URL. Signed upload tokens use Supabase's expiry. Abandoned uploads can remain as unreferenced private objects; no scheduled deletion is enabled in this first version.

The app stores preferences for future reminders, but it does not execute automation, send outbound messages, approve inspections automatically, or move money. Payment records are administrative records only.
